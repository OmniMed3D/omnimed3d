# PRD 5.3.1 마스크 조립 아키텍처 재검토

Epic 3/4(Parse Worker/Inference Worker) 착수 전, REQ-C04(워커 간 데이터 흐름 계약)를 정리하다가 "3D 마스크를 최종적으로 누가 조립하는가"를 별도로 재검토한 기록. PRD 5.3.1은 현재 **엔진이 슬라이스별 2D 마스크를 받아서 자체 브릭 아틀라스에 조립**하는 구조로 돼있음 — 이게 최선인지 대안들과 비교 검토한다.

## 현재 설계가 왜 근거 있는 선택인지

핵심 근거는 PRD 5.3.1의 "Engine Integration Point" 문구: 엔진은 마스크 채널을 **HU 볼륨용으로 이미 만들어야 하는 브릭/페이지테이블 스트리밍 인프라**(대용량 볼륨이 VRAM을 초과할 때 쓰는 브릭 단위 스트리밍, PRD 1.3)에 채널 하나로 얹어서 소비한다. 즉 마스크 때문에 새로 만드는 조립 시스템이 아니라, 원래 있어야 하는 시스템을 재사용하는 구조 — "redundant JS-side compositing layer"를 피하겠다는 PRD의 명시적 의도와 일치한다.

## 검토한 대안과 기각 이유

### 대안 1 — Inference Worker가 3D 마스크를 통째로 조립해서 한 번에 전달

- **지연시간 파괴**: 5.3.1의 "AI 추론 완료를 기다리지 않고 볼륨부터 렌더링, 마스크는 점진적으로 채운다"는 핵심 결정과 정면 충돌. 150장 시리즈·슬라이스당 500ms 목표 기준, 최악의 경우 마스크가 뜨기까지 약 75초 소요 — 완전히 다른 체감 성능이 된다.
- **메모리 부담**: Inference Worker가 전체 마스크 볼륨을 들고 있어야 해서 PRD 10.1의 OOM 리스크를 키운다.
- **트랙 간 결합도 증가**: AI 트랙이 엔진의 내부 브릭 주소 체계를 알아야 바로 소비 가능한 포맷을 만들 수 있다 — 지금 설계(AI는 규격화된 2D 슬라이스만 뱉으면 끝)보다 결합이 세진다.
- **기각.**

### 대안 2 — 별도의 "마스크 조립 전용" 워커 신설

- 엔진도 Inference Worker도 아닌 제3의 워커가 조립을 맡는 안. 결국 엔진의 브릭 주소 체계에 깊이 결합되거나(분리 실익 없음), 자체 단순 포맷을 만들어 엔진이 다시 변환해야 한다 — 워커만 늘고 이득이 없다.
- **기각.**

## 결론

현재 PRD 설계(엔진이 기존 브릭 인프라로 조립)가 검토한 대안들 대비 타당하다. AI 트랙 책임은 "규격에 맞는 2D uint8 슬라이스를 뱉는 것"까지로 깔끔하게 한정되고, 3D 조립은 엔진이 어차피 필요한 인프라를 재사용한다 — 중복 없음, 점진적 렌더링 철학 유지, 트랙 간 결합 최소화.

## PRD가 명시 안 해서 확인 필요한 것 (REQ-C04 계약에 포함)

1. **엔진(WASM)이 실제로 어디서 실행되는지** — 메인 스레드인지 자체 워커인지 PRD/다이어그램에 불명. Inference Worker → 엔진 마스크 전달이 몇 홉을 거치는지(메인 스레드 경유 여부)에 영향을 준다.
2. **Inference Worker → 엔진 구간도 Transferable(zero-copy)로 넘기는지** — REQ-A15는 Parse Worker의 두 출력(HU 볼륨, 전처리 텐서)에 대해서만 명시돼 있고 이 구간은 명시가 없다. 다만 마스크 슬라이스는 512×512 uint8 기준 약 256KB로, HU 볼륨(수백MB~GB급)보다 훨씬 작아 위험도는 낮다.

두 항목 모두 설계 결함이 아니라 "글로 안 적혀서 Daewon과 맞춰야 하는 디테일" — REQ-C04 계약 정리할 때 같이 포함시킬 것.
